# 一条主线，两套安装包

2026-11-02起采用此协作方式；当前整合入口为草稿PR #3。它仍待检查与实机验收，不表示已合入。

## 如何开发

- `main`是两台设备唯一共同起点；额度中心、平台读取器、界面与版本号共享。
- Mac与Windows在各自短期功能分支开发。开始前fetch并核对main；修改相同的主进程/界面/打包配置时先对齐，不用另一台机器整目录覆盖。
- 每个PR都运行双平台检查；平台专属观察器和启停保留独立模块。功能通过后回到main，不再长期保留一条Mac产品线。
- 当前先完成PR #3整合；此期间新增工作仍从main开始，经PR评审。整合PR在合入前再次同步main并重跑检查。
- 本地存在未提交改动时先保留，使用独立工作树；不要为切换主线清理旧改动。

## 如何验收

Check工作流对同一个提交分别构建Windows x64和Mac Apple Silicon。检查包含依赖安装、自动检查、原生编译、打包完整性；Mac还执行原生自检及签名结构检查。两个任务全部成功后统一门禁才通过。

安装包保存在对应Actions运行的Artifacts内，名字带平台和被测提交SHA，保留7天。这是候选包，不是GitHub Release；没有上传到Releases、发版标签或自动安装步骤。PR检查可能基于GitHub生成的合并提交，下载时以该次运行SHA为准。

每项任务强制20分钟上限；新提交取消同PR旧运行。无定时轮询、无模型调用、无自动重试；失败先看日志定位，修复后再运行。只用标准GitHub托管运行器，不配置付费大型运行器。当前Mac范围为Apple Silicon；Intel不在承诺范围内。

自动通过后，两台真实设备分别验收候选的额度中心、原小仪表、启停、设置保存和已有授权下的只读额度连接。Mac另验权限、菜单栏、更新控件避让/归位、跨屏及休眠；Windows另验安装、置顶、定位及通知。历史版本验收只作参考，不能冒充新候选已经通过。

## 如何发布

- 同一版本号、同一源代码提交、同一个GitHub Release页面，放Windows安装程序/ZIP和Mac DMG/ZIP；用户按系统下载。
- 新功能没有准备好的平台要明确写支持状态；不能为保持版本数字一致伪造验收或重新上传不同代码却冒用相同版本号。
- 0.4.4已存在，本次候选沿用其版本用于整合验证，不覆盖既有发行资产。真正发行时根据届时main统一确定一个尚未使用的新版本，并同步package.json、lock、浏览器组件及版本说明。
- 合入main与正式发布是两个独立决定。用户授权发布后，才复核源提交、双平台检查、真实设备结果、凭据/个人数据、校验和及签名/公证状态，创建Release。
- 当前Mac候选仅ad-hoc签名，未公证；Windows现有未签名边界保持。自动构建成功不能宣称完成签名发行。
- 某一平台未通过时保留上一份可用安装包，不覆盖它；另一平台的候选可用于验收，但不能称为已完成统一跨平台发布。

运行器与构建产物机制依据GitHub官方资料（2026-11-02核对）：[运行器](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)、[构建产物](https://github.com/actions/upload-artifact)。
